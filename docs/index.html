OWASP Juice Shop
Threat Model

An architecture-led STRIDE assessment, organized around the four questions in MDN’s example threat model.

Status: design-review draft; no runtime tests performed. This is a complete baseline document for the stated scope, not a verified assessment of a pinned release. Application version, commit, deployment, control implementation and residual-risk approval remain unconfirmed. Threat scenarios below are hypotheses, including those inherited from the earlier conversation.

Overview

Juice Shop is assessed as a shop application whose accounts, data and administrative actions must be protected. Two operating profiles are kept separate: a deliberately vulnerable training lab, and a hypothetical hardened application. Hardening recommendations describe the latter; lab operators should preserve teaching flaws while isolating the environment.

The official architecture establishes Angular, Express/Node.js, SQLite, Sequelize/finale-rest, MarsDB, WebSocket challenge notifications and Google OAuth 2.0 [S1]. Logical responsibilities such as authentication and shop business logic are modeling abstractions. The four-question document structure follows MDN [S2].

1. What are we working on?

Scope and assumptions

  • In scope: client rendering, HTTP API, identity and authorization responsibilities, shop workflows, relational and document data access, WebSocket access, external identity integration and relevant configuration.
  • Out of scope: browser-engine flaws, OS/kernel compromise, physical access and provider infrastructure internals. Application configuration that exposes the host remains in scope.
  • No production bank system or real payment provider is assumed. No payment-card processing or blockchain service is added.
  • All browser input and caller-supplied identifiers are untrusted; attackers may call the API directly.
  • Baseline OS/browser protections are assumptions, not verified controls. TLS, reverse proxies, session storage and audit infrastructure are unknown.
  • No exact vulnerability, library version, JWT algorithm issue or exploit payload is asserted from architecture alone.

Security objectives

Only the correct identity can establish a session; every action is authorized for its actor and object; data remains private and accurate; shop invariants hold under hostile requests; resource use remains bounded; significant actions are auditable.

2. What can go wrong?

Method and prioritization

STRIDE: S = spoofing, T = tampering, R = repudiation, I = information disclosure, D = denial of service, E = elevation of privilege. Labels describe relevant effects, not a forced one-to-one mapping.

Inherent priority is a workshop estimate, not measured exploitability or CVSS. Likelihood: 1 requires unusual prerequisites, 2 is plausible but conditional, 3 is broadly reachable if the hypothesized control failure exists. Impact: 1 localized, 2 one account or limited disruption, 3 multiple users, administrative authority or server/service compromise. Score = likelihood × impact: 1–2 Low, 3–4 Medium, 6 High, 9 Critical. Ratings are conditional on each flaw existing; they are not evidence that it does.

Threat register

T1 — Login injection and authentication bypass

S/T · score 9/9

Affected elements / flows
C3,C4,C7,C8; F2,F3,F8
Assets
A1,A2,A3
Scenario and consequence
An unauthenticated caller supplies input that changes a login query, bypassing identity checks.
Response R1 — Reduce
Use bound parameters for every login query; keep identity decisions independent of query text.
Validation V1
Submit malformed and boundary-case login inputs; invalid credentials never establish a session.
Proposed accountable role
Backend / AppSec

T2 — Forged or misused session credentials

S/E · score 9/9

Affected elements / flows
C4; F2,F3
Assets
A1,A2,A6
Scenario and consequence
An attacker presents altered, expired, incorrectly signed, or wrong-audience credentials and gains an identity or role. Token format and library are not established by the architecture.
Response R2 — Reduce
Use maintained session libraries; enforce signature, issuer, audience and expiry where applicable; define revocation and secure storage.
Validation V2
Reject altered, expired and wrong-context credentials. If JWT is used, reject disallowed algorithms and unsigned tokens.
Proposed accountable role
Identity / Backend

Assets
A1,A2,A3

T14 — Unprotected transport or OAuth integration

T/I/S · score 6/9

Affected elements / flows
C1,C3,C4,E1; F1,F2,F10,F11
Assets
A1,A2,A3
Scenario and consequence
An on-path attacker reads or changes traffic, or an incorrectly bound OAuth flow establishes the wrong identity. TLS termination and OAuth exchanges are deployment-dependent.
Response R14 — Reduce
Enforce HTTPS/WSS and secure proxy configuration; validate OAuth state and exact redirect URIs; use PKCE where supported; use OIDC for identity when applicable.

Proposed accountable role

Cross-cutting coverage and limits

  • Apply authorization checks to WebSocket connections and messages if they expose user-specific information or accept commands; do not infer that challenge notifications include private business data.
  • Review NoSQL operator handling independently from SQL parameter binding.
  • For cookie-backed authentication, assess CSRF and cookie flags; for bearer tokens, assess storage and exfiltration. The storage choice is not known here, so neither approach is assumed.
  • Review OAuth callback and token handling against the actual implementation. The browser-provider line is deliberately high-level.
  • Dependency compromise, SSRF, file traversal and parser-specific attacks require a feature/source inventory. T13 is conditional coverage, not proof that all these features exist.

3. What are we going to do about it?

Training-lab operating profile

Accepting deliberately exploitable application behavior can be appropriate only inside an authorized training environment. The operator must separately approve that scope. Use synthetic data, disposable accounts, no reused production credentials, restricted inbound access, constrained outbound connectivity, least-privileged containers/processes, resource limits and a reset procedure. Do not expose host secrets, container-control sockets or unrelated sensitive volumes. These are proposed containment requirements, not verified deployment features.

Hardened-application operating profile

Implement R1–R14, verify controls through V1–V14, and reassess likelihood and impact with evidence. Hardening may intentionally break training challenges; maintain a separate branch or environment rather than silently changing the lab’s learning objectives.

Residual risk

Residual ratings are not assessed. Control descriptions do not justify lowering risk until implementation and test evidence exist. Record any acceptance with the accountable owner, reason, scope, expiry date and compensating controls.

4. Did we do a good enough job?

Current review status

  • Architecture inventory, flow inventory and 14 threat hypotheses are documented.
  • Each threat has a proposed response, validation criterion and owner role.
  • No source-code audit, runtime test, deployed-control check or residual-risk approval has been performed.
  • The model is ready for a review workshop; it is not a security sign-off.

Validation and sign-off gates

  1. Pin the Juice Shop release/commit, image digest and deployment diagram; reconcile all component and flow IDs with implementation.
  2. Confirm session design, OAuth legs, generated endpoints, parser/upload/fetch entry points, data classifications and WebSocket behavior.
  3. Execute V1–V14 only in the authorized isolated environment. Record date, build, tester, evidence and result; mark non-applicable tests with justification.
  4. For a hardened profile, block release on unaddressed Critical/High findings unless formally accepted; agree numerical availability budgets before load testing.
  5. Obtain architecture, application-security and service/lab-owner review; name real owners and target dates.

Open questions

  1. Which application release, source commit and deployment configuration are authoritative?
  2. Is the intended profile a local disposable lab, a shared training platform or a hardened demonstration?
  3. Where is TLS terminated, and which origins, routes and WebSocket endpoints are reachable?
  4. How are sessions stored, validated, expired and revoked? What are the actual OAuth callbacks?
  5. Which generated resources and fields are exposed? Where are ownership and role checks enforced?
  6. Which uploads, templates, XML parsers, outbound fetches and privileged filesystem paths exist?
  7. What data, logs, backups, administrative access and dependency pipelines are present?

Review cadence

Revisit after identity, route, data-flow, dependency or deployment changes and after incidents; conduct a scheduled review at least annually. This cadence follows the review approach in MDN’s example [S2].
